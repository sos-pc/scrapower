# Audit technique — Scrapower (juillet 2026)

> Audit global post-cleanup v0.7.1. Couvre coordinateur, workers, harvesters,
> packaging, CI et docs. Complète `audit-2026-06.md` (les items encore ouverts
> de juin sont référencés).

---

## Synthèse

L'architecture est saine : séparation coordinateur / worker claire, protocole
Mode B simple et robuste (pull + assignment_token), blob store content-addressed,
harvester unifié par comptes. Le cleanup v0.7.1 a bien réduit le code mort.

Mais trois problèmes critiques subsistent, dont un **trou d'authentification
sur `/worker/submit` et `/worker/heartbeat`** avec écriture de fichier dont le
chemin est contrôlé par le client, et la **fuite de blobs (B12/A8 de juin)
toujours pas corrigée** — le GC ne supprime jamais rien.

---

## 🔴 Critique

### C1 — `/worker/submit` et `/worker/heartbeat` sans authentification ni rate-limit

**Fichiers** : `worker_gateway/http_handler.py:164-257`, `worker_gateway/router.py:31-102`

`pull()` vérifie `X-API-Key`, mais `submit()` et `worker_heartbeat()` n'ont
**aucune** vérification. Conséquences pour un attaquant non authentifié :

1. **Écriture de fichier arbitraire (path traversal)** : `_save_worker_logs()`
   construit `Path("data/logs") / f"{task_id}.log"` avec un `task_id` issu du
   **corps JSON** (pas du routing). `task_id = "../../n'importe/où"` → append
   de contenu attaquant-contrôlé dans tout chemin inscriptible se terminant
   par `.log`. Idem via `worker_id` dans heartbeat et pull.
2. **Remplissage disque** : logs appendus sans limite de taille, sans auth,
   sans rate-limit.
3. **Manipulation d'état** : le chemin d'erreur de `submit()` (`exit_code != 0`,
   http_handler.py:217-231) appelle `transition(task_id, TIMEOUT)` **sans
   vérifier l'assignment_token** — il suffit de connaître un task_id ASSIGNED
   pour brûler ses retries jusqu'à FAILED.

**Fix** : exiger `verify_api_key()` sur submit + heartbeat ; valider
`task_id`/`worker_id` (regex `^[a-f0-9-]{8,64}$`) avant tout usage en chemin ;
exiger le token sur le chemin d'erreur de submit ; plafonner la taille des logs.

### C2 — Fuite de blobs : le GC ne supprime jamais rien (B12/A8 juin, toujours ouvert)

**Fichiers** : `blob_store.py`, `task_manager.py:154-159`, `domain.py:232-237`

`store_blob()` crée avec `ref_count=1` (et +1 à chaque re-store) ; `create()` /
`set_queued()` / `complete()` incrémentent encore ; `cleanup_expired()` ne
décrémente que 1 par référence tâche. Le ref_count ne retombe **jamais** à 0,
`run_gc()` ne collecte donc jamais (`delete_blob()` est du code mort, aucun
appelant). Croissance disque non bornée — aggravée par le seed du
whisper_runner (+1 par redémarrage).

**Fix** : choisir une sémantique unique (ex. store = ref 0, seules les tâches
possèdent des refs), supprimer `delete_blob()` ou l'utiliser.

### C3 — Corruption d'encodage (mojibake) dans les sources

**Fichiers** : `coordinator/main.py` (~1 500 séquences `ÃÂ...`),
`harvester/kaggle.py` (81 séquences `â`)

Docstrings, commentaires et séparateurs ont subi au moins un double
ré-encodage UTF-8→Latin-1. Le code compile, mais les fichiers se dégradent à
chaque édition et les commentaires sont illisibles.

**Fix** : réécrire les commentaires/docstrings touchés en UTF-8 propre ;
ajouter `.editorconfig` (charset utf-8) pour éviter la récidive.

## 🟠 Élevé

### E1 — `complete()` : transaction non annulée en cas de rejet

**Fichier** : `task_manager.py:316-339`

Si le blob de sortie est introuvable, la fonction retourne False en croyant que
« la transaction rollback » — faux. L'`UPDATE tasks SET output_hash` reste dans
la transaction implicite ouverte de la connexion **partagée**, et sera commité
par le prochain `commit()` de n'importe quelle autre requête. Résultat :
output_hash fantôme sur une tâche restée ASSIGNED. Ajouter un
`await self._db.rollback()` sur les chemins d'échec.

### E2 — Fallback `exit_code=2` documenté mais inexistant

**Fichiers** : `ARCHITECTURE.md` (§ Reactive fallback), `http_handler.py:217`

Le worker émet bien `exit_code=2` (`whisper_runner.py:233` via `DownloadError`),
mais le coordinateur traite tout code non nul comme TIMEOUT générique. Le
téléchargement de secours côté coordinateur (« coordinator DL → audio_hash →
requeue ») n'existe nulle part. Après 3 échecs de download → FAILED.
Soit réimplémenter, soit purger la doc et le code worker du signal 2.

### E3 — `requeue_for_worker()` : code mort ET buggé

**Fichier** : `domain.py:191-207`

Aucun appelant (le zombie_watchdog WS a été supprimé). S'il était appelé, il
persisterait l'état brut `'timeout'` sans passer par `transition()` — état que
ni `requeue_stale()` (filtre ASSIGNED) ni `cleanup_expired()` ne rattrapent :
tâche coincée à vie. Supprimer.

### E4 — Surcomptage `workers_active` : total global affecté à chaque compte

**Fichiers** : `kaggle.py:63`, `modal.py:61-62,88-89`, `ephemeral.py:80-84`

`refresh()` fait `registry.update_workers(aid, len(self._kernel_refs))` — le
**total** de kernels/sandboxes du provider est attribué à **chaque** compte.
`_tick()` fait ensuite `sum(a.workers_active ...)` → total multiplié par le
nombre de comptes → `total_active >= queued` trop tôt → le harvester
sous-lance des workers. Tracker les refs par compte.

### E5 — Message d'erreur écrit dans `output_hash`

**Fichier** : `domain.py:249-255`

Le nettoyage des PENDING expirés écrit `'download lost after coordinator
restart'` dans la colonne `output_hash` au lieu de `error`. Donnée polluée,
exposée par `GET /tasks/{id}`.

### E6 — `asyncio.create_task` fire-and-forget sans référence forte

**Fichier** : `transcribe_api.py:93,224`

Les tâches `run_prepare()` ne sont référencées nulle part : le GC Python peut
les collecter en plein vol (pitfall asyncio documenté) → tâche coincée en
PENDING (puis FAILED par TTL 1 h). Garder un `set` de références +
`add_done_callback(discard)`.

## 🟢 Mineur / hygiène

- `cursor = cursor = await ...` ×3 (`task_manager.py:164,191,280`).
- Versions incohérentes : `0.1.0` (pyproject, FastAPI, `/health`) vs `0.7.1` (`/`).
- `ruff` per-file-ignores référence `auth_oauth.py`, supprimé depuis.
- Config vs réalité : `heartbeat_interval_sec=10` (config) vs 30 s codé en dur
  worker ; `ARCHITECTURE.md` dit « COMPLETED/FAILED supprimés après 24 h », le
  code dit 30 jours ; `keepalive_*`, `default_verification_mode`,
  `max_anonymous_workers`, `task_accept_timeout_sec` chargés mais inutilisés.
- `to_launch: list[tuple[str, asyncio.Task]]` — ce sont des coroutines
  (`ephemeral.py:94`) ; `ensure_running()` hors interface `WorkerProvider`.
- Worker : upload du blob ré-exécuté à chaque retry de submit ; log « OK: … »
  même en cas d'échec (`loop.py:209`).
- `modal.cleanup_stale()` fait 2 `_save_state()` (SQLite sync) par tick de 15 s.
- Parsing CSV Kaggle naïf (virgules dans les titres).
- Commentaires FR/EN mélangés.

## Documentation obsolète (ARCHITECTURE.md)

- Mode A WebSocket, `/worker/ws`, `SCRAPOWER_WS_ASSIGN_ENABLED` : plus aucune
  trace dans le code.
- Types de tâches `wasm`/`fetch` : supprimés.
- « Reactive fallback exit_code=2 » : inexistant (cf. E2).
- « cleanup après 24 h » : 30 jours en réalité.
- Interface `WorkerProvider` documentée avec `remaining_pct()/has_quota()/status()` :
  l'interface réelle est `refresh()/launch_worker()/cleanup_stale()`.

## Tests

La suite a été supprimée volontairement (commit `a9a13ac`). La CI ne fait que
ruff + mypy. Vu la densité de bugs d'état (C2, E1, E3, E5), une petite suite
ciblée (lifecycle des tâches, comptabilité ref_count, auth des endpoints
worker) aurait un ROI élevé — ce sont précisément les régressions que lint et
typage ne voient pas.

## Priorités recommandées

1. **C1** — auth + validation de chemin sur submit/heartbeat (surface publique).
2. **C2** — sémantique ref_count + réactiver le GC (le disque se remplit).
3. **E1/E5** — intégrité des données tasks (rollback, bonne colonne).
4. **E4** — comptage par compte (le harvester sous-lance aujourd'hui).
5. **C3** — réencoder main.py / kaggle.py avant que ça ne s'aggrave.
6. **E2 + docs** — trancher : réimplémenter le fallback ou purger doc + signal.
