# Audit Scrapower — juillet 2026

> Complément à `BUGS.md`, pas une redite. Lecture complète du repo fourni, en traçant plusieurs flux de bout en bout (soumission de tâche → DB → matching de capacités → pull worker → heartbeat → submit → GC) pour voir où les couches se contredisent, plutôt que fichier par fichier isolément. Format calqué sur `BUGS.md` (🔴/🟡/🔵) pour fusion facile dans votre tracking.
>
> **Angle mort assumé** : `security.py` n'est pas dans les fichiers fournis. C'est le fichier qui vérifie la clé API et fait le rate limiting — le plus sensible de l'appli. Rien ci-dessous ne porte dessus ; à auditer en priorité si vous voulez une couverture sécu complète.

## 1. Personne ne garantit que `Task` reflète vraiment la ligne SQL

Je mets ça en premier parce que ça explique une partie des bugs qui suivent.

`db.py` a un système de migrations "best effort" :

```python
for sql in migrations:
    try:
        await db.execute(sql)
    except Exception:
        pass
```

N'importe quelle erreur — colonne déjà là (le cas attendu), mais aussi disque plein, DB verrouillée, corruption — est avalée silencieusement (déjà noté en BUGS #18). Conséquence visible : `task_manager.py` ne fait jamais confiance au schéma et vérifie `"colonne" in row.keys()` avant de lire — sauf que cette prudence est appliquée de façon incohérente, et surtout **incomplète**.

### 1.1 `get()` ne relit pas `task_type`, `requirements_json`, `deadline_ms`, `max_retries`, `definition_json`
- **Fichier** : `task_manager.py::get()`
- **Problème** : le `SELECT *` ramène toutes les colonnes, mais la reconstruction du `Task(...)` n'en réutilise qu'une partie. `task_type` et `requirements_json` retombent sur les defaults du dataclass (`"whisper"`, `"{}"`), `deadline_ms` sur `60000`, `max_retries` sur `3` — peu importe la vraie valeur en base.
- **Impact concret** : `transition()` appelle `self.get(task_id)` puis teste `task.can_retry` (= `retries < max_retries`). Comme `max_retries` est toujours `3` via `get()`, le jour où vous voudrez un `max_retries` différent par type de tâche (probable vu la roadmap multi-workload), le comportement de retry sera silencieusement faux pour toute tâche passée par `get()`. Aujourd'hui ça ne se voit pas parce que **toutes** les tâches sont créées avec `max_retries=3` — la coïncidence masque le bug, elle ne le corrige pas.
- **Action** : factoriser un seul `_row_to_task(row)` utilisé à la fois par `get()` et `get_queued()`, pour qu'il n'y ait plus qu'un seul endroit à tenir à jour.

### 1.2 `get_queued()` ne relit pas `deadline_ms` → le matching de capacités ment déjà, en silence
- **Fichiers** : `task_manager.py::get_queued()`, `domain.py::_match_capabilities()`, `http_handler.py::pull()`
- **Problème** : déjà en partie dans BUGS #22, mais voici la conséquence concrète. `_match_capabilities()` compare `task.deadline_ms` à `capabilities["lifecycle"]["expected_remaining_sec"]`. Les tâches whisper sont créées avec `deadline_ms=900000` (15 min, dans `transcribe_api.py`), mais `get_queued()` ne relisant jamais cette colonne, le `Task` vu par `pull()` a toujours `deadline_ms=60000` — la coordination ment sur la vraie deadline.
- **Pourquoi ça ne casse rien aujourd'hui** : aucune capability construite par `entry.py::_build_capabilities()` ne renseigne `expected_remaining_sec` — la branche est morte pour l'instant. Le jour où vous l'activerez, un worker en fin de vie pourra se voir attribuer une tâche de 15 min en croyant qu'elle dure 60s.
- **Action** : même remède que 1.1.

### 1.3 Le garde-fou `"col" in row.keys()` est appliqué au hasard
Détail amusant en creusant : les colonnes du schéma **d'origine** (`current_assignment_token`, `assigned_worker_id`, `executable_hash`, `runtime`, `gpu_required`...) sont vérifiées défensivement, alors qu'elles n'ont *jamais* été ajoutées par migration — la vérification n'a jamais été utile pour elles. À l'inverse, `deadline_ms` et `max_retries`, ajoutées par `ALTER TABLE` (donc les seules vraiment à risque), ne sont même pas lues du tout. Ça sent le code qui a suivi le schéma au fil des `ALTER TABLE` sans être revu une fois stabilisé — la prudence a été copiée au mauvais endroit et jamais appliquée là où elle comptait.

## 2. Le multi-comptes Kaggle/Modal ne fait pas ce que la v0.7 promet

- **Fichiers** : `harvester/kaggle.py::refresh()`, `harvester/modal.py::refresh()`
- **Problème** :

```python
# kaggle.py
for aid in self._account_ids:
    ...
    registry.update_workers(aid, len(self._kernel_refs))
```
```python
# modal.py — répété dans la branche cache ET la branche refresh complet
for aid in self._account_ids:
    registry.update_workers(aid, len(self._sandbox_ids))
```

`self._kernel_refs` / `self._sandbox_ids` sont des listes **globales à tout le harvester**, pas par compte. Chaque compte se voit donc attribuer le total tous comptes confondus, pas son propre total.

- **Impact** : `Account.can_launch` bloque dès que `workers_active >= max_concurrent` (3, hardcodé pour les deux providers dans `main.py`). Avec 3 comptes Kaggle et un seul kernel actif sur chacun (3 au total, 1 chacun), les 3 comptes affichent `workers_active=3` et se bloquent mutuellement — alors qu'individuellement aucun n'est à sa limite. Tout le principe de la v0.7 ("plus de comptes = plus de capacité", `remaining_pct()` par compte, `asyncio.gather` sur plusieurs comptes) est neutralisé : la capacité totale reste plafonnée à `max_concurrent` peu importe le nombre de comptes ajoutés.
- **Action** : `kernel_id` contient déjà le username en préfixe — compter par compte plutôt que globalement :
```python
count = sum(1 for k in self._kernel_refs if k.startswith(f"{username}/"))
```
Pour Modal, étendre `self._sandbox_tokens` (déjà un mapping sandbox→credentials) pour inclure l'`account_id` et filtrer pareil.

## 3. Sécurité — gravité variable, à trier

### 3.1 `PUT /blobs` lit tout le corps avant de vérifier l'auth ou la taille
- **Fichier** : `main.py::upload_blob()`
```python
async def upload_blob(request: Request, _rate=Depends(rate_limit)):
    body = await request.body()          # ← tout bufferisé ici
    ...
    is_worker = assignment_token and await _verify_assignment_token(db, assignment_token)
    is_admin = verify_api_key(request)
    if not is_worker and not is_admin:
        return JSONResponse({"error": "UNAUTHORIZED"}, status_code=401)
    if len(body) > cfg.max_blob_size_mb * 1024 * 1024:
        return JSONResponse({"error": "PAYLOAD_TOO_LARGE"}, status_code=413)
```
- **Problème** : auth et taille sont vérifiées *après* avoir chargé tout le body en RAM. `max_blob_size_mb` protège le disque, pas la mémoire du process.
- **Impact** : DoS mémoire possible sur un endpoint exposé publiquement (Caddy + CORS `*`). `rate_limit` limite la fréquence, pas la taille d'une requête unique.
- **Action** : vérifier `Content-Length` (idéalement streamer/limiter la lecture) et l'auth via headers/query params — tous deux disponibles avant tout `await request.body()`.

### 3.2 Le rate limit par worker est contournable en une ligne
- **Fichier** : `http_handler.py::pull()`
- **Problème** : `worker_id` vient du corps de la requête sans lien vérifié avec l'identité de l'appelant. `rate_key = worker_id`. Avec la clé API partagée, n'importe quel appelant peut envoyer un `worker_id` aléatoire à chaque appel pour ne jamais taper les 30 pulls/min.
- **Impact** : limité par votre modèle de menace actuel (usage perso, clé partagée), mais le rate-limit perd son sens, et un `worker_id` préfixé `hf-` généré n'importe comment fausserait aussi `mode_b_active_count("hf-")`.
- **Action** : documenter que ce n'est pas une vraie protection anti-abus tant qu'il n'y a pas d'identité de worker vérifiée (token par worker délivré au premier contact), plutôt que de laisser croire à une garantie qui n'existe pas.

### 3.3 CORS `*` + headers d'auth, pour une fonctionnalité qui n'existe pas encore
- **Fichiers** : `cors_middleware.py`, `ARCHITECTURE.md`
- **Constat** : `Access-Control-Allow-Origin: *`, avec `x-api-key`/`authorization` explicitement autorisés en cross-origin — pour le futur worker navigateur (WASM/WebGPU), listé "Planned (future)". Pas urgent, mais évitez d'exposer une surface permissive avant que la fonctionnalité qui en a besoin existe. `ALLOWED_ORIGINS = ["*"]` (BUGS #34, jamais utilisée) devrait au moins être branchée plutôt que le hardcode `b"*"`.

### 3.4 Le mot de passe SOCKS5 (WireGuard) transite en clair sur l'internet public
- **Fichiers** : `deploy/vpn-wg/dante.conf`, `docker-compose.yml`
- **Constat** : exposer le port 1081 publiquement est un choix cohérent (Kaggle/Modal doivent le joindre depuis des IP non prévisibles), contrairement au port 1080 (loopback-only, usage interne). Mais l'auth SOCKS5 username/password (RFC 1929) n'est pas chiffrée au niveau protocole, et la connexion `socks5://scrapower:PASS@...` n'est pas enveloppée en TLS. Le mot de passe transite en clair entre worker et coordinateur.
- **Impact** : réel mais borné — au pire un accès résidentiel via votre WireGuard, pas un accès à l'API ou aux données.
- **Action** : pas de fix simple sans complexité significative (stunnel devant 1081). À minima, rotation périodique du mot de passe, à ne pas traiter comme un secret long terme.

### 3.5 Isolation client (`X-Client-ID`) purement déclarative
- **Fichier** : `client_api.py`
- **Constat** : le bypass "anonymous" a été corrigé (SESSION_DOC du 18/06), mais le modèle reste : `X-Client-ID` est un header non authentifié, auto-déclaré. Avec une seule clé API partagée, n'importe qui devinant un `client_id` (ex. `"cli"`, le défaut de `cli/main.py`) peut se faire passer pour lui.
- **Action** : si outil mono-opérateur, documenter que `X-Client-ID` est une convention et non une frontière de sécurité. Sinon, il faudrait une clé par client.

### 3.6 Secrets/infra en clair dans des fichiers trackés
- **Fichiers** : `Makefile` (IP `130.110.242.56`, chemin de clé SSH `clouscard-ghost.key`), `SESSION_DOC.md` (mêmes infos, répétées plusieurs fois)
- **Constat** : `.gitignore` exclut `BUGS.md` explicitement — vous faites déjà la distinction "doc à ne pas exposer" — mais pas `SESSION_DOC.md`, qui contient pourtant les mêmes informations d'infra. Incohérence dans votre propre politique.
- **Action** : paramétrer le Makefile via `.env` (déjà fait pour `SCRAPOWER_WG_PASS`), et soit gitignorer `SESSION_DOC.md`, soit en retirer les commandes `scp`/`ssh` avec IP en dur.

### 3.7 La clé API est écrite en clair dans le notebook Kaggle poussé sur leur plateforme
- **Fichiers** : `kaggle.py::_start_kernel()`, `sworker.ipynb`
- **Constat** : `os.environ["SCRAPOWER_API_KEY"] = "{{API_KEY}}"` est substitué en dur dans le code source de la cellule avant `kaggle kernels push`. Le kernel est privé, mais Kaggle a une vraie fonctionnalité "Secrets" faite pour ça (injection à l'exécution, jamais dans le code versionné). Là, la clé apparaît dans le JSON du notebook et son historique de versions côté Kaggle.
- **Action** : utiliser les secrets Kaggle plutôt que la substitution de template.

## 4. Le worker ne vérifie jamais les codes HTTP — trois symptômes du même oubli

- **Fichier** : `worker/loop.py`

**a) Téléchargement de blob** — aucune vérification de `r.status` :
```python
async with session.get(f"{self.coordinator_url}/blobs/{...}", ...) as r:
    executable = await r.read()
```
Si le blob n'existe pas (404), `executable` devient le corps JSON de l'erreur, que le worker tente ensuite d'exécuter comme script Python — `SyntaxError` immédiate, loggée comme bug de tâche alors que c'est un blob manquant.

**b) Upload de résultat** :
```python
up = await r.json()
output_hash = up.get("hash", output_hash)
```
Si l'upload est rejeté (413, 401...), le code retombe silencieusement sur le hash local et croit avoir réussi. Le serveur rejette bien le `complete()` ensuite (bonne protection côté `task_manager.py`), mais le worker gaspille 3 tentatives sans jamais savoir que la vraie cause est "fichier trop gros" — très difficile à diagnostiquer depuis les logs.

**c) Pull** :
```python
if r.status >= 500:
    ...continue
data = await r.json()
break
```
Un `401` (clé révoquée) ou `429` tombe dans la branche normale, `data.get("task")` renvoie `None`, et le worker se comporte comme "pas de tâche" jusqu'à l'idle timeout. Une panne d'authentification devient indiscernable d'une file vide dans les logs.

- **Action** : dans les trois cas, vérifier `r.status` explicitement avant de faire confiance au corps de la réponse, logger distinctement 401/413/429.

## 5. Le heartbeat dit "tâche invalide" mais n'arrête rien

- **Fichier** : `worker/loop.py::_heartbeat()` / `run()`
- **Problème** : quand le coordinateur répond `task_valid: false` (tâche réattribuée après 90s de silence), le worker fait `self._log_task_id = ""` puis `return` — ça arrête la coroutine de heartbeat, mais **pas** le subprocess en cours (`execute_python()` continue jusqu'au bout ; aucun mécanisme d'annulation entre les deux coroutines).
- **Impact** : le worker termine la tâche, upload, soumet — et se fait rejeter côté serveur (token périmé). Calcul gaspillé, sur une plateforme où le GPU-heure est la ressource rare et budgétée. Se déclenche par un simple blip réseau de 90s+ pendant qu'un worker travaille encore réellement — pas besoin d'un vrai crash.
- **Action** : porter un signal d'annulation (`asyncio.Event` partagé, vérifié par `_run_task`, avec `proc.kill()` si levé) entre `_heartbeat` et l'exécution en cours.

## 6. La configuration n'atteint quasiment jamais la prod

### 6.1 `config/coordinator.toml` n'est jamais monté dans le conteneur
- **Fichiers** : `config.py::load_config()`, `docker-compose.yml`, `Dockerfile`
- **Constat** : `load_config()` cherche `config/coordinator.toml`. Ni les volumes de `docker-compose.yml` (`data/`, `deploy/`, `src/`) ni le `Dockerfile` (`COPY src/`, `COPY deploy/`) ne rendent un tel fichier accessible dans le conteneur. Sauf mécanisme non montré ici, le TOML n'est jamais chargé en prod.
- **Et les env vars ne couvrent pas tout** : `_apply_env_overrides()` ne gère que `host`, `port`, `data_dir`, `db_path`, `max_blob_size_mb`, `max_task_retries`, `blob_ttl_days`, `log_level`, `coordinator_url`. Le reste — `heartbeat_interval_sec`, `heartbeat_miss_threshold`, `checkpoint_ttl_days`, `max_anonymous_workers`, `keepalive_*`, `default_verification_mode` — n'a ni override env ni TOML pour l'atteindre : figé sur les defaults du dataclass, sans moyen de changer sans toucher au code.
- **Impact** : `default_verification_mode` (trust/challenge/redundant), qui a l'air pensé comme un vrai levier opérationnel, n'est concrètement configurable nulle part dans le déploiement actuel.
- **Action** : monter un vrai TOML, ou compléter `_apply_env_overrides()` pour couvrir tous les champs — ou les deux.

### 6.2 Trois constantes de "délai avant de considérer que c'est mort", indépendantes
- **Fichiers** : `loop.py` (`HEARTBEAT_INTERVAL_SEC = 30`), `session.py` (`max_age_sec=90`, hardcodé), `domain.py::requeue_stale()` (`silence_timeout_sec=90`, hardcodé), `config.py` (`heartbeat_interval_sec=10`, `heartbeat_miss_threshold=3`)
- **Problème** : `SessionManager.__init__` accepte `heartbeat_interval_sec`/`heartbeat_miss_threshold`... et ne les stocke jamais (BUGS #30). Résultat : 4 endroits portent, sous des noms différents, un même concept, avec des valeurs reliées par aucun calcul explicite (30 dans `loop.py` ; 10×3=30 dans `config.py`, jeté à la poubelle ; 90 codé en dur à deux endroits, sans lien affiché avec le 30 de `loop.py`, alors que 90 = 30×3 est probablement voulu).
- **Action** : une seule source de vérité dans `Config`, un seul calcul `stale_after = heartbeat_interval_sec * heartbeat_miss_threshold`, propagé partout — au lieu de "90" recopié à la main.

## 8. Code mort qui redeviendrait dangereux si quelqu'un le rappelle

- **Fichier** : `domain.py::requeue_for_worker()`
- **Problème** : passe par une `UPDATE ... SET state = 'timeout'` brute, en court-circuitant `transition()`. Or `transition()` ne laisse *jamais* une tâche dans l'état `TIMEOUT` littéral — il redirige immédiatement vers `QUEUED` (retries incrémenté, tokens nettoyés) ou `FAILED`. `requeue_for_worker()` laisserait une tâche bloquée pour toujours dans un état `timeout` que plus aucun code ne sait requeue, nettoyer ou même voir (`get_queued()` filtre sur `queued`, `cleanup_expired()` sur `completed/failed/cancelled`, `requeue_stale()` sur `assigned`) — fuite de tâche et de ses blobs référencés, permanente.
- **Bonne nouvelle** : rien n'appelle cette méthode dans les fichiers fournis — c'est un pont vers le "zombie_watchdog" du Mode A (WebSocket), supprimé. Le bug ne s'exprime pas aujourd'hui.
- **Action** : la supprimer avec le reste du nettoyage Mode A, ou la corriger pour passer par `transition()`. Même chose pour la branche `ASSIGNED` de `transition()` (accepte un `worker_id`, duplique `TaskManager.assign()`) — semble elle aussi sans appelant restant.

## 9. Gestion des dépendances — trois symptômes du même laisser-aller

- **`httpx` mal classé** : `cli/main.py` fait `import httpx` en top-level (utilisé par `serve` et `submit`), mais `httpx` n'est déclaré que dans `[project.optional-dependencies].dev` de `pyproject.toml`, jamais dans `dependencies`. Un `pip install scrapower` normal (sans `[dev]`) casse la commande `scrapower` dès l'import du module. Pas remarqué parce que le `Dockerfile` n'utilise jamais l'entrée `scrapower` (il lance `python -m scrapower.coordinator.main` directement).
- **Dockerfile non pinné, dupliqué par rapport à `pyproject.toml`** : `pip install fastapi "uvicorn[standard]" pydantic aiosqlite aiofiles structlog aiohttp cryptography kaggle faster-whisper yt-dlp modal huggingface_hub` — aucune version, liste maintenue à la main en parallèle de `pyproject.toml` qui a de vraies bornes. Un rebuild Docker peut installer des versions différentes d'un jour à l'autre.
- **Le patch `kagglesdk` peut échouer en silence** :
```python
c = c.replace(old, new)
```
`str.replace()` sur une chaîne absente ne lève rien. Si une future version de `kagglesdk` reformate même légèrement la ligne patchée, le build continue, affiche `"kagglesdk patch applied"` (inconditionnel, sans vérifier que le remplacement a eu lieu), et le bug `TimeDeltaSerializer` d'origine revient sans que rien ne le signale avant un crash en prod.
- **Action commune** : `pip install -e ".[dev]"` dans le Dockerfile plutôt qu'une liste parallèle ; déplacer `httpx` dans `dependencies` ; `assert old in c, "kagglesdk source has changed, patch needs review"` dans `patch_kagglesdk.py`.

## 10. Petits pièges, vite corrigés, qui trahissent un manque de relecture

- **I/O synchrone bloquant la boucle asyncio** : `blob_store.py::store_blob()` fait `mkdir`/`write_bytes`/`os.replace` en synchrone dans une fonction `async def`, sur un endpoint appelé à chaque upload de résultat par chaque worker. Même souci pour `http_handler.py::_save_worker_logs()`. BUGS #26 ne signale ce pattern que pour `modal.py`, mais c'est plus impactant ici : ça bloque tout l'event loop (donc tous les `pull`/`heartbeat` en cours) pendant l'écriture d'un blob potentiellement gros.
- **Violation de couche répétée** : `task_service._tm._db.execute(...)` appelé directement depuis *trois* endroits (deux méthodes de `domain.py`, déjà BUGS #19, plus `http_handler.py::_touch_task()` et le handler heartbeat de `router.py`, non mentionnés dans BUGS). La même opération ("prolonger le bail d'assignation") réimplémentée trois fois en SQL brut. Un `TaskManager.touch(task_id)` unique réglerait les trois.
- **`import os` inutilisé** dans `_save_worker_logs()` — jamais référencé dans le corps.
- **`cursor = cursor = await ...`** : confirmé à `get()`, `get_queued()`, `assign()` (BUGS #21 correct sur ces emplacements).
- **`_purge_orphaned_assignments()`** (`main.py`) fait un `SELECT` puis boucle un `UPDATE` par ligne — alors qu'un `UPDATE ... WHERE state = 'assigned'` unique (comme le fait déjà `requeue_for_worker()`) ferait la même chose en une requête, avec `cursor.rowcount` pour le compte.
- **Logique d'activation Kaggle bancale** dans `main.py::_build_registry()` : `if not kaggle_enabled and not a.get("enabled", True): continue` ne saute que si les deux flags sont désactivés ensemble ; dans tous les autres cas de désactivation, le compte est quand même ajouté au registre (inoffensif plus loin, mais rend `/stats` incohérent : désactivé par un seul flag → visible ; par les deux → invisible). Le code Modal équivalent n'a pas cette branche et est plus simple — à aligner.
- **`ModalHarvester._create_sandbox()`** reconstruit `WG_PROXY` à la main via `SCRAPOWER_COORDINATOR_URL.replace("https://", "")` (ne gère pas `http://`) au lieu de réutiliser `SCRAPOWER_WG_PROXY_PUBLIC`, qui existe déjà correctement construite dans l'environnement du coordinateur et que `kaggle.py` utilise déjà correctement.
- **`blob_store.py::store_blob()`** : `SELECT` puis `INSERT` sans transaction ni `INSERT OR IGNORE` — deux stockages concurrents du même contenu (même hash) peuvent se heurter sur la `PRIMARY KEY`. Fenêtre étroite, non gérée.
- **`run_gc()`** : `SELECT` puis `DELETE` avec la même clause au lieu d'une requête unique (en plus d'être dupliqué checkpoint/régulier, BUGS #17) — risque théorique très faible vu le filtre d'ancienneté, mais autant simplifier.

## 11. Ce qui est bien fait

- Validation stricte du hash dans `_blob_path()` avant construction du chemin disque — protection réelle contre le path traversal.
- `assign()`/`complete()` dans `task_manager.py` : pattern "UPDATE conditionnel + `cursor.rowcount`" pour détecter les races — la bonne façon de faire une assignation atomique sans verrou explicite.
- Séparation loopback (port 1080, sans auth) / internet-exposé (port 1081, avec auth) entre proxy VPN interne et proxy WireGuard — cohérent avec leurs usages respectifs.
- `scripts/bundle_modal_worker.py` : bonne réponse à un vrai problème (duplication manuelle Kaggle/Modal), génération automatique plutôt que synchronisation à la main.
- Durcissement Docker du coordinateur (`read_only`, `cap_drop: ALL`, `no-new-privileges`) — rare sur un projet perso.
